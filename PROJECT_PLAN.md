# DLA Medical Supply Readiness Agent — Project Plan

## 1. Project purpose

This repository supports the DataRobot Senior AI Solutions Engineer — Federal interview take-home assignment.

The goal is to build and present a technically credible MVP of an AI agent that solves a high-value Federal enterprise problem while remaining easy for a mixed technical/business audience to understand.

The selected scenario is a **DLA Medical Supply Readiness Agent** for **Defense Logistics Agency (DLA) Troop Support Medical**.

The solution intentionally demonstrates more than conversational RAG. It combines:

- large-scale structured operational data in Databricks,
- governed SQL/data-analysis capabilities,
- unstructured policy retrieval,
- a DataRobot predictive model for future shortage risk,
- agent orchestration in DataRobot,
- and a clear path toward simulation and human-approved actions.

All operational records generated by this repository are **synthetic**. Public DLA scale metrics are stored separately with provenance and must never be represented as generated operational facts. The policy corpus is also explicitly synthetic and must never be represented as official DLA, DoD, or DHA policy.

---

## 2. Business problem

DLA Troop Support Medical supports a large and operationally critical medical supply chain. Supply planners must anticipate shortages while reconciling inventory, demand, open orders, supplier lead times, shipment delays, backorders, expiration risk, mission priority, readiness requirements, and governing policy.

The underlying information naturally spans three information types:

1. **Structured operational data** — inventory, orders, shipments, suppliers, customers, consumption, and historical performance.
2. **Unstructured governing context** — medical supply policies, stocking requirements, contingency guidance, and sourcing procedures.
3. **Predictive risk** — a model-generated estimate of whether a currently acceptable supply position will fall below minimum stock within the next 30 days.

The difficult task is combining these sources quickly enough to identify risk before mission impact and explain why the risk exists.

### Million-dollar question

> **Which critical medical supplies are at risk of shortage over the next 30 days, where will those shortages occur, why, and what should we do about them?**

This question anchors the entire data model, predictive model, tools, agent, and live demo.

## 4. Primary user and demo persona

The primary persona is a **DLA medical supply planner / readiness analyst** preparing for an operational readiness review.

The user should be able to ask questions such as:

- Which mission-critical medical items are closest to shortage?
- Which locations have the greatest 30-day shortage risk?
- Why is a particular item/location combination at risk?
- Is demand increasing, or is inbound supply the larger driver?
- Which suppliers are causing the most exposure?
- What policy or stocking requirement applies to this item?
- What evidence supports the recommendation?

The experience should feel like an analytical teammate that can use governed tools, not a chatbot guessing from text.

## 5. Core architecture

```text
User
  |
  v
DataRobot Readiness Agent / Orchestrator
  |
  +------------------------------+-----------------------------+
  |                              |                             |
  v                              v                             v
Tool 1                         Tool 2                        Tool 3
Operational Analyst           Policy RAG                   Shortage Risk Lookup
Databricks Genie              DataRobot-native RAG         Deterministic lookup
  |                              |                             |
  | Managed Genie MCP            v                             v
  v                         DataRobot vector DB         DataRobot batch prediction
Operational Delta tables      + LLM blueprint           output in Databricks

Future production tools: scenario simulation and human-approved action creation.
```

Key architectural principles:

> **The agent reasons. Tools analyze. The predictive model predicts.**

> **Tool 1 explains what is happening. Tool 2 explains what rules apply. Tool 3 returns the authoritative model risk.**

The LLM should not ingest or reason directly over millions/billions of raw operational rows. Structured tools execute aggregation where the data lives and return only the result needed for reasoning.

The three MVP tools intentionally have separate responsibilities. In particular, the DataRobot shortage prediction tables are **not exposed to Genie**. This preserves a deterministic boundary around predictive inference and prevents the operational analyst from becoming an all-purpose tool.

### Tool 3 — Shortage Risk Prediction Lookup

**Status: predictive pipeline ✅ COMPLETE; deterministic agent lookup still to build**

**Implementation: deterministic lookup against the DataRobot batch prediction output stored in Databricks. This tool does not use Genie and does not ask an LLM to generate SQL.**

Predictive pipeline already established:

```text
Databricks ml_shortage_scoring
        |
        v
DataRobot deployed shortage-risk model
        |
        v
DataRobot batch prediction job
        |
        v
Databricks ml_shortage_predictions_raw
```

Purpose:

- retrieve the authoritative DataRobot-generated probability for an item/location pair,
- expose the current 30-day shortage risk to the agent,
- keep model output separate from exploratory operational analysis,
- prevent the LLM or Genie from inventing or reinterpreting a predictive probability.

Target modeled by DataRobot:

`shortage_within_30d`

Conceptually:

```text
P(fall below minimum stock threshold in next 30 days | information available today)
```

Intended tool interface:

```text
get_shortage_risk(customer_id, item_id)
```

Minimum response fields:

- `snapshot_date`
- `customer_id`
- `item_id`
- `shortage_probability_30d`

Conceptual responsibility:

> **Tool 3 answers: what probability did the DataRobot predictive model assign?**

## 7. Databricks data-generation approach

The synthetic data layer is generated **directly as managed Delta tables using PySpark**. There is no CSV staging layer for operational data.

Design goals:

1. Reproducible from code.
2. Runnable from a single Databricks notebook.
3. Modular enough that generation logic is not all contained in one notebook.
4. Portable between Databricks workspaces/catalogs.
5. Large enough to demonstrate why tool-based SQL aggregation matters.
6. Small enough to run economically for interview development.
7. Statistically structured enough to support a legitimate shortage-risk model.

### Catalog behavior

`databricks/notebooks/00_generate_all.py` is the primary entry point.

If the `catalog_name` widget is blank, the notebook uses:

```python
spark.catalog.currentCatalog()
```

Default schema:

```text
dla_medical_supply_demo
```

Normal destination:

```text
<current_catalog>.dla_medical_supply_demo.<table>
```

For the interview, the synthetic world should remain frozen to a known as-of date/seed so predictions and demo answers remain reproducible.

## 9. Delta table design and purpose

### Dimensions

- `dim_customer_location` — one synthetic receiving/customer location; region, service, mission priority, supported population, remote-location indicator.
- `dim_medical_item` — one synthetic medical item; commodity group, FSC-style category, criticality, unit cost, stocking requirement, shelf life, cold-chain flag, policy reference.
- `dim_supplier` — one synthetic supplier; type, geography, lead time, baseline on-time performance, quality rate.
- `bridge_customer_item` — active customer-item relationship; preferred supplier, baseline demand, minimum and target days supply.

### Operational facts

#### `fact_inventory_daily`

Grain:

> customer × medical item × day

Measures include daily demand, on-hand units, on-order units, backorders, expiration exposure, days of supply, minimum/target days supply, inventory status, and inventory value.

This is the main large-data table for demonstrating aggregation at scale.

#### `fact_orders`

Requisitions/orders with customer, item, supplier, priority, quantities, status, promised delivery date, and value.

#### `fact_shipments`

Shipment performance with promised/actual delivery, days late, on-time flag, and shipped units.

#### `fact_supplier_events`

Interpretable disruptions such as manufacturing constraints, transportation delays, quality holds, cold-chain exceptions, raw-material shortages, and capacity reductions.

### Agent/analytics products

#### `analytics_supplier_performance`

Aggregated supplier delivery performance for efficient root-cause analysis.

#### `agent_current_supply_position`

Current agent-ready operational table combining the fields most useful in a live investigation: location, item, criticality, inventory, days of supply, demand context, backorders, late inbound supply, supplier performance, estimated stockout context, and policy reference.

**It must not contain the DataRobot shortage prediction.**

### ML products

#### `ml_shortage_training`

Historical point-in-time feature rows with target:

`shortage_within_30d`

A positive label means the customer-item pair was above minimum at the snapshot date and fell below that minimum within the following 30 days.

Rows already below minimum at prediction time are excluded from future-shortage training cases.

#### `ml_shortage_scoring`

Current feature state for batch scoring by the DataRobot model. There is one current row per active customer-item relationship and no future label.

#### `ml_shortage_predictions_raw`

DataRobot batch prediction output written back to Databricks. This is the authoritative current prediction source for Tool 3 and is intentionally excluded from Tool 1 / Genie.

## 10. Synthetic shortage-generation philosophy

The shortage target must be **learnable and explainable**, not a random label.

Synthetic dynamics create shortages through observable conditions such as:

- low/decreasing days of supply,
- increasing or volatile demand,
- backorders,
- long supplier lead time,
- weak supplier on-time performance,
- late inbound units,
- remote geography,
- disruption events,
- mission/customer stocking requirements.

Hidden latent variables may be used internally to create correlated behavior, but they **must never appear in persisted model features**.

### Point-in-time / leakage requirement

Features at date `T` may only use information available on or before `T`.

The target may look forward from `T` through `T + 30 days`.

The target should remain a minority event with enough positive cases for DataRobot to learn meaningful patterns.

### Predictive-AI message

> **The agent reasons. DataRobot's predictive model predicts.**

### Tool-specialization message

> **Genie explains operations. RAG explains policy. The DataRobot model quantifies future risk.**

The three-tool design is intentional. A specialized tool should own each information type rather than turning a single general-purpose assistant into the source of every answer.

### Federal governance message

The architecture should naturally support discussion of:

- least privilege,
- read-only tools,
- identity propagation,
- approved schemas,
- user authorization,
- auditability,
- source attribution,
- human approval for consequential actions,
- deterministic controls around model reasoning.

### MVP message

The MVP builds the three capabilities that make the demo credible:

1. governed structured-data analysis through Databricks Genie,
2. grounded policy retrieval through DataRobot RAG,
3. predictive shortage risk through a DataRobot model and deterministic lookup tool.

Scenario simulation and operational action execution remain explicit production extensions rather than rushed demo features.
